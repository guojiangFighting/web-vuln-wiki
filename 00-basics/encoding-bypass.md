# 编码与绕过（Encoding & Bypass）

## 一句话
> 「绕过」的根源不是攻击者聪明，而是同一段数据在链路上要被多层解析器各解码一次——凡是解码次数或顺序不一致的地方，防御看到的东西和最终执行的东西就可能不一样。

## 核心机制：一层解码一次

一个 Web 请求通常要经过：`浏览器 → WAF/CDN → Web 服务器 → 应用框架 → 数据库/模板引擎/Shell`。每一层都可能做一次解码或转义：

1. **WAF** 规则匹配它看到的第一层字节；
2. **Web 服务器**解码 URL；
3. **框架**解码一次或多次；
4. **最终执行器**（SQL、模板、Shell）按自己的语法再解释一遍。

**防御有效的前提**：校验发生在「最后一层解码完成之后」。任何一层「提前校验、后面又解码」，校验对象和执行对象就脱节了。

## 编码速查表

| 编码 | 形态示例（字符 `/`） | 常见用途 |
|------|--------------------|----------|
| URL 编码 | `%2F` | HTTP 传输保留字 |
| 双重 URL 编码 | `%252F`（`%25` 是 `%`） | 打「WAF 解码一次、应用解码两次」 |
| HTML 实体 | `&#47;` `&sol;` | 进入 HTML 语境的转义 |
| 十六进制字面量 | SQL 中 `0x2F` | 引号被过滤时替代字符串 |
| Unicode/宽字节 | `%C0%AF`（宽字节） | 多字节编码拼接吃掉转义反斜杠 |
| Base64 | `Lw==` | 传输而非过滤，但常被误当「加密」 |
| 注释符 | `/**/`、`--`、`#` | SQL 内部拆分关键字或注释后缀 |
| 大小写变化 | `SeLeCt` | 只做小写匹配一次替换的过滤 |
| JSON 转义 | `\u002F` | JSON body 中的等价变体 |

## 多层解码示例

以路径穿越探测 `..%252fetc%252fpasswd` 为例：

| 阶段 | 看到的内容 | 判断 |
|------|-----------|------|
| WAF（解码一次） | `..%2fetc%2fpasswd` | 不是 `../`，放行 |
| 应用框架（再解码一次） | `../etc/passwd` | 危险语义生效 |

同一份字节，**WAF 看到的和文件系统收到的是两个东西**——这就是全部绕过技巧背后唯一的原理。反过来，SQL 关键字大小写、注释拆分（`uni/**/on`）、双写（`ununionion`）则是在「同一层」内对抗特征匹配：**匹配找的是固定模式，语法执行认的是等价变体**。

## 与漏洞的关系
- [SQL 注入](../10-injection/sql-injection.md)：十六进制字面量替代引号字符串、注释符绕空格过滤、大小写混写。
- [XSS](../20-frontend/xss.md)：payload 在 HTML 属性里可用实体编码，在 JS 里可用 `\u` 转义，进入的语境决定哪种编码有效。
- [路径穿越](../40-files-requests/path-traversal.md)：`../` 的全部变体本质都是编码层错位。
- [SSTI](../10-injection/ssti.md) / [命令注入](../10-injection/command-injection.md)：同理——「校验的字符集」与「最终语法认的字符集」不一致。

## 安全要点
1. **尽早归一化**：入口处先完成全部解码（到字节层），再校验；校验后的数据不许再被「无意义地」解码。
2. **解码后校验，输出时编码**：校验只做一次（在归一化数据上），输出按目标语境（SQL/HTML/Shell）用对应参数化或编码函数处理。
3. **拒绝含糊**：含双重编码、非法百分号序列、过长编码的请求直接拒绝（400），不要尝试「纠正」。
4. 白名单优于黑名单：与其枚举「恶意编码」，不如定义「合法字符集之外全部拒绝」。

## 常见误区
- **「过滤 = 在输入上 replace 掉危险词」**：过滤必须发生在归一化之后，否则过滤的是上一层的幻影。
- **「Base64 能防注入」**：Base64 只是编码，解码后照常执行；把它当防御是混淆「传输格式」与「信任边界」。
- **「WAF 拦了就安全」**：WAF 是特征匹配的旁路防御，见[怎么理解绕过](#核心机制一层解码一次)——治本永远是参数化与语境化输出。
- **「绕过手法要背很多」**：变体无穷，原理只有一条——防御视角与执行视角的解析不一致。
