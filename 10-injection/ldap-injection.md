# LDAP 注入（LDAP Injection）

## 一句话
> 用户输入被拼进 LDAP 查询过滤器，输入里的括号与 `*` 通配符改写了过滤条件——和 SQL 注入同根，但利用面更窄：没有 UNION，主要靠条件真假与返回条数说话。

## 它是怎么发生的
**根因**：数据与过滤器语法未分离。LDAP 的查询是一段字符串过滤器（filter），形如：

```
(&(objectClass=user)(uid=alice))
```

`&` 是 AND、`|` 是 OR、`!` 是 NOT，括号包条件，`*` 通配。当用户输入直接拼进 `uid=` 后面：

```python
f"(&(objectClass=user)(uid={username}))"
```

输入 `*` 变成 `(&(objectClass=user)(uid=*))`——匹配所有用户；输入 `admin)(|(uid=*` 则能改写整个过滤器结构。

**触发三要素**：
1. 输入进入 LDAP 查询（企业 SSO、通讯录搜索、统一身份认证系统最常见）；
2. 字符串拼接构造过滤器；
3. 响应差异可观察（查询结果条数、登录成功与否、报错）。

## 攻击场景

### 场景一：通配符枚举
**目标**：探测目录中存在的用户。**思路**：单字符 + `*` 前缀匹配，逐字符推进。
**payload**：`a*` → `ab*` → `adm*` …
**结果**：搜索接口的返回条数差异暴露用户名，行为等同布尔盲注。

### 场景二：恒真条件绕过
**目标**：登录/认证逻辑中绕过校验。**思路**：构造永真过滤器。
**payload**：`*)(uid=*))(|(uid=*`
**结果**：过滤器被改写为「任意 uid 为真」，认证逻辑失守（是否成立取决于应用如何使用查询结果）。

### 场景三：属性注入取数据
**目标**：让响应携带其他属性（如邮箱、部门）。**思路**：闭合当前条件后追加对敏感属性的匹配。
**结果**：在企业目录场景中可横向摸清组织结构——LDAP 注入的价值主要在这类「信息架构泄露」。

### 场景四：盲探测
**目标**：无直接回显时。**思路**：用「登录成功/失败」「返回条数」「响应时间」作为过滤器真假的信号通道。
**结果**：与布尔盲注同节奏。

## 怎么发现它
- **手工测试**：找到「查人/认证/组织架构」功能，输入 `*` 看是否返回异常多的结果；输入括号类 payload `*)(` 观察是否报错或行为变化。
- **真假判断**：`*` 在普通搜索框本来就是合法的模糊匹配输入，单凭通配符命中不构成漏洞——要证明**结构被改写**（如 `)(` 引起报错或条件被追加）才算。LDAP 特殊字符（`* ( ) \ / NUL`）的转义是否生效是核心判断点。

## 常见绕过与进阶
- **前端只过滤了一部分字符**：`*` 被滤但 `(` `)` 没滤（或反之），构造仍可能成立。
- **编码层**：LDAPv3 支持 `\XX` 十六进制转义，过滤器层与应用层的转义责任划分不清时出缝。
- 思路主线：与所有注入一致——**确认转义发生在哪一层、覆盖了哪些字符、有没有结构字符漏网**。

## 怎么修
1. **参数化/转义 API（治本）**：用语言与库提供的 LDAP 转义函数处理所有插入过滤器的值（`* ( ) \ /` 与 NUL 五个字符必须转义），或使用支持参数化过滤器的库。
2. **输入白名单**：用户名按「字符集 + 长度」严格校验后再进过滤器。
3. **最小权限绑定**：LDAP 连接账号只授必要子树读权限，禁匿名与高权 bind。
4. **结果集限制**：搜索接口限制返回条数与字段，压低枚举收益。

## 常见误区
- **「LDAP 注入能像 SQLi 一样拖库」**：LDAP 没有 UNION/堆叠，单次查询能力有限；它的现实危害集中在枚举、绕过与结构泄露，评估时别套用 SQLi 的危害模板。
- **「搜索框支持 `*` 就是漏洞」**：通配符是产品功能；漏洞在于**结构字符（括号）未被转义**导致过滤器语义可被改写。
- **「企业内网系统不用管」**：LDAP 恰恰集中部署在内网 SSO 与目录服务，恰是横向移动的关键节点。
