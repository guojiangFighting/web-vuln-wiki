# SQL 注入（SQL Injection）

## 一句话
> 用户输入被拼进 SQL 语句并改变了语句的结构，攻击者因此能读写数据库中的任意数据，严重时进一步控制服务器。

## 它是怎么发生的
**根因**：代码把「数据」和「代码」混在同一条字符串里拼接发送给数据库。数据库收到的是一条完整的 SQL，它无法区分哪部分是开发者写的语法、哪部分是用户给的数据——只要输入里恰好含有 SQL 语法，它就会被执行。

典型危险写法（PHP 示意）：

```php
$sql = "SELECT * FROM users WHERE name = '" . $_GET['name'] . "'";
```

当 `name` 参数传入 `' OR '1'='1` 时，最终语句变成：

```sql
SELECT * FROM users WHERE name = '' OR '1'='1'
```

`OR '1'='1'` 是恒真条件，原本「按用户名过滤」的语义被彻底改写——这就是注入与「输入校验不严」的本质区别：**不是脏数据进了库，而是语句结构被改了**。

**触发三要素**：
1. 用户可控输入进入 SQL 语句（source：GET/POST 参数、Cookie、Header、JSON 字段，甚至 `Referer`、`X-Forwarded-For`）；
2. 用字符串拼接或未参数化的方式构造语句（sink：`query` / `execute` / ORM 的原生查询出口）；
3. 数据库的行为差异能被观察到——有报错回显、有布尔差异、有时间差异，或能发起带外连接。

**数据流**：`用户输入 → 业务代码字符串拼接 → SQL 引擎解析执行`。链路上任何一处做了「输入是可信的」假设，漏洞就成立。

## 攻击场景

### 场景一：恒真条件绕过登录（字符型，有回显）
**目标**：不输密码登录。**思路**：在过滤条件上追加恒真分支。
**payload**：用户名填 `' OR '1'='1`，密码随意。
**结果**：语句变成 `WHERE name='' OR '1'='1'`，返回表里第一行，通常即管理员。这类测试必须确认目标属于授权范围。

### 场景二：UNION 联合查询拖库（有回显）
**目标**：把任意表的数据拼进正常响应。**思路**：UNION 前后列数必须一致，先用 `ORDER BY` 或逐列 `NULL` 探测列数，再找页面会回显的列，最后替换为子查询。
**payload**（MySQL，探测列数→读表）：

```sql
' ORDER BY 5-- -          -- 报错则列数 <5，递减探测
' UNION SELECT NULL,table_name,NULL FROM information_schema.tables-- -
```

**结果**：页面正常区域出现表名，再对 `columns` 表重复同样手法即可逐步取数。

### 场景三：报错注入
**目标**：无数据回显但有数据库报错回显时取数。**思路**：构造必然报错的表达式，把想读的数据塞进报错文本。
**payload**（MySQL）：`' AND extractvalue(1, concat(0x7e, (SELECT version())))-- -`
**结果**：报错信息中带出 `~8.0.36` 这样的数据。一次一个值，需循环拼接。

### 场景四：布尔盲注
**目标**：页面无数据回显，但「查询成功/失败」会引起页面差异。**思路**：把问题改写成一连串真假判断，如「当前数据库名第一个字符的 ASCII 是否大于 64」，按二分法逐字符猜解。
**payload**：`' AND (SELECT ASCII(SUBSTRING(database(),1,1)))>64-- -`
**结果**：对比两种响应的差异（长度、关键词），恢复出完整数据。效率低但普适。

### 场景五：时间盲注
**目标**：连布尔差异都没有时。**思路**：让数据库按条件延迟响应，用响应时间当信号。
**payload**（MySQL）：`' AND IF(1=1, SLEEP(5), 0)-- -`
**结果**：条件为真时响应慢约 5 秒。注意网络抖动会带来假信号，需多次取样。

进阶：堆叠查询（`stacked queries`，取决于驱动是否允许多语句）、数据库写文件（`INTO OUTFILE`，需 DBA 权限与可控路径）、`sqlmap --os-shell` 的原理即「写文件 + 找到可访问路径」。这些已属于「从拖库到 RCE」的升级链。

## 怎么发现它
- **手工测试**：在每个疑似 sink 处先做「语法探测」——字符型点加 `'` 看是否报错，数字型点做加减运算（`?id=2-1` 与 `?id=1` 结果是否一致）观察行为差异；再按「报错 → UNION → 布尔 → 时间」的顺序降级尝试。
- **工具**：授权测试中可用 `sqlmap -u "<url>" -p id --batch --level=2` 做自动化确认；Burp 的 Intruder 配合 SQL 错误关键字字典可做粗筛。务必控制并发与请求量。
- **真假判断**：`'` 引起 500 不一定是注入（可能只是类型错误）；确认要看「语法是否真的被执行」——如 `' AND '1'='1` 与 `' AND '1'='2` 两条除了布尔值外完全一致，若响应稳定地一个正常一个异常，才是强证据。时间盲注要排除网络抖动，重复取样。

## 常见绕过与进阶
- **空格过滤**：用注释代替 `/**/`，或括号包裹函数调用 `sleep(5)`。
- **关键字过滤**：大小写混写、内联注释拆词 `uni/**/on`、双写 `ununionion`（针对只做一次替换的过滤）。
- **引号过滤**：数字型点无需引号；字符串可用十六进制字面量 `0x616263` 代替 `'abc'`。
- **WAF 语义识别**：换等价函数（`extractvalue` 换 `updatexml`）、换编码层次（URL 双重编码打「WAF 解码一次、应用解码两次」的错位）。
- 思路主线只有一个：**WAF 匹配的是特征，数据库执行的是语法——找出两边理解不一致的地方**。

## 怎么修
1. **参数化查询（预编译）为唯一治本方案**：SQL 语法在预编译阶段定型，输入只作为参数绑定，永不参与语法解析。所有语言都有对应 API（JDBC `PreparedStatement`、Python DB-API、PHP PDO）。ORM 的查询构造器默认安全，但 `raw()` / `rawQuery()` 出口仍会注入。
2. **无法参数化的部分用白名单**：`ORDER BY` 字段名、排序方向、表名来自用户时，映射到服务端固定选项，绝不拼接原文。
3. **最小权限**：应用数据库账号只授必要表的必要操作，禁 `FILE` 权限与多库访问，让「即使注入也拖不动全库」成立。
4. **不向用户暴露数据库报错**：统一错误页，报错只进日志。这不是修复注入，而是消除报错注入这一利用面。
5. **纵深**：输入校验仍值得做（如 id 必须为整数），但把它当收紧数据的方式，而不是当注入的修复。

## 常见误区
- **「过滤了关键字就安全」**：过滤只提高门槛不改变本质，大小写、注释、编码、等价函数都能绕。只有参数化改变「数据参与解析」这一根因。
- **「用了 ORM 就不会注入」**：ORM 只在参数绑定层面安全；拼接进 `where("name = '" + input + "'")`、原生 SQL、动态表名同样中招。
- **「预编译可以护住整条语句」**：表名、列名、关键字不能参数化——这是 SQL 语法的一部分，不是值。这类位置必须白名单。
- **「注入只是泄露数据」**：取决于数据库权限与配置，还可能读写文件、执行系统命令（如 `xp_cmdshell`、UDF），从数据泄露升级为服务器失陷。
