# JWT 攻击（JWT Attacks）

## 一句话
> JWT 的安全性完全押在「签名被正确校验」这一件事上——alg 可控、密钥误用、声明不校验，任何一处出错，攻击者就能伪造任意身份的令牌。

## 它是怎么发生的
**根因**：JWT = `base64(header).base64(payload).base64(signature)`，前两段只是编码不是加密。安全性依赖三点同时成立：签名算法不可控（服务端说了算）、签名必校验、关键声明（`exp`/`iss`/`aud`）必校验。实现时任何一处「信任了令牌自己说的话」，就等于把身份权威交给了请求方。

**先建立两个基础认知**：
1. **签名 ≠ 加密**：payload 任何人可解码阅读（base64），敏感数据放进去就是泄露；
2. **签名的意义**：持有密钥的一方保证 payload 未被篡改——校验方的工作是「验证」，不是「阅读并相信」。

## 攻击场景

### 场景一：alg 置 none
**目标**：未校验算法的解析库。**思路**：JWT 头里 `alg` 是令牌自述的——把签名去掉、`alg` 改为 `none`，若库接受「无签名令牌」，伪造即成功。
**payload**：`{"alg":"none","typ":"JWT"}` + 伪造的 payload + 空签名
**结果**：以任意身份通过校验。本质：**身份声明应该由服务端决定，却读了令牌的自述**。

### 场景二：RS256 → HS256 密钥混淆（Key Confusion）
**目标**：服务端「按令牌的 alg 选择验证方式」。**思路**：服务端用 RS256（非对称：私钥签、公钥验）签发，但验签代码支持 HS256（对称：同一密钥）——把**公钥**当 HS256 的密钥签一个新令牌。公钥是公开的（如从 JWKS 端点取），攻击者能拿到它，就能造出合法签名。
**结果**：签名校验通过，身份任意。条件是「验签代码信任令牌的 alg」——同一根因的场景二形态。

### 场景三：不校验签名（或只解码）
**目标**：把 `jwt.decode` 当 `jwt.verify` 用的代码。**思路**：改 payload 直接发。
**结果**：最基础的形态——「解码成功」被当成「验证成功」。

### 场景四：声明不校验
**目标**：签名正确但声明宽松。**思路**：逐项试——`exp` 删掉或改成未来（不过期令牌）、`iss`/`aud` 随意值（跨系统令牌通用）、**`kid` 注入**（`kid` 参数拼进密钥查询/路径，构造 SQL 注入或路径穿越选择攻击者控制的密钥）。
**结果**：伪造面从「签名」转移到「声明语义」——校验逻辑的每一项缺省都是一条伪造通道。

## 怎么发现它
- **手工测试**：拿到合法令牌后解码（base64 即可，无需工具），检查 payload 中的角色/用户 id 字段；依次构造「alg:none」「HS256+公钥作密钥」「改角色重签（若可自签）」等令牌，观察服务端是否接受；测 `exp` 删除、`iss` 乱填、`kid` 注入。
- **工具**：jwt.io 类解码器 + Burp 的 JWT 扩展做编辑与重签；授权环境下可用 hashcat 对 HS256 弱密钥做字典测试（密钥弱 = 全站伪造）。
- **真假判断**：伪造令牌被接受才是漏洞；「返回 500」可能是解析异常而非接受；区分「签名校验失败 401」与「声明校验缺失 200」——后者更隐蔽也更常见。

## 常见绕过与进阶
- **jku/jwk 头注入**：令牌自带「公钥地址」，若服务端按头取密钥即指向攻击者托管密钥。
- **弱 HMAC 密钥**：字典可破，破一次 = 长期伪造任意令牌。
- **算法实现缺陷**：个别库的 RSA 填充或 ECDSA nonce 重用——属深度研究，测试中记为「检查库版本」。
- 思路主线：**JWT 的每个「自述字段」（alg/kid/jku）都是「令牌对验签方说的话」，验签方一条都不能信**。

## 怎么修
1. **算法白名单硬编码（治本第一）**：验签代码里固定 `RS256`（或选定算法），无视令牌头的 alg；禁用 `none`。
2. **用成熟库的正确 API**：`verify`（校验）而非 `decode`（解码）；issuer/audience/exp 作为 verify 参数强制传入。
3. **密钥管理**：HS256 密钥足够长（≥256 位随机）；RS256 私钥只存签名服务；`kid` 仅作索引查找固定密钥表，绝不拼进 SQL/文件路径。
4. **声明最小心智**：payload 不放敏感数据（base64 可读）；令牌只做「身份凭证」，权限判断每次查服务端状态（角色变更、封禁即时生效）。
5. **令牌轮换与撤销**：短 TTL + refresh token + 服务端黑名单（与[会话管理](session-management.md)同一课题）。

## 常见误区
- **「JWT 加密了我的数据」**：base64 是编码，解码即明文；需要机密性用 JWE 或不传敏感数据。
- **「签名校验通过就万事大吉」**：alg:none/密钥混淆的本质都是「校验逻辑被令牌自述带偏」；「校验了」与「校验对了」是两件事。
- **「JWT 比 Session 天然安全」**：无状态是双刃剑——「无法主动失效」意味着改密/封禁后旧令牌仍有效，直到过期。JWT 不解决会话管理问题，只是换了它。
- **「alg 由谁选无所谓」**：这是所有 JWT 攻击的单一根因——**算法选择权必须永远在验签方**。
