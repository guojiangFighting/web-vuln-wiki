# 服务端请求伪造（SSRF）

## 一句话
> 应用替用户发起网络请求且目标可控——攻击者借用服务器的网络位置，访问它才能访问的东西：内网服务、云元数据、本机端口。服务器是攻击者的「网络代理」。

## 它是怎么发生的
**根因**：服务端代码需要「抓取用户给的 URL」（功能上很常见），却把整个 URL 当作目标直接请求，没有限制「能去哪」。

典型危险写法（示意）：

```python
resp = requests.get(request.form["avatar_url"])   # 拉取用户提供的头像
```

`avatar_url` 传入 `http://169.254.169.254/latest/meta-data/`，请求就从**服务器**发出去了——注意方向：[CSRF](../20-frontend/csrf.md) 是「借用户的浏览器发请求」，SSRF 是「借服务器的网络发请求」。

**常见 sink（哪里会出现用户可控 URL）**：URL 预览（聊天/文档贴链接出缩略图）、webhook 配置、文件/数据导入（按 URL 拉取）、HTML 转 PDF、图片处理（远端图片 URL）、爬虫功能。

**危害阶梯（评估时按此定位）**：
1. 内网/本机存活与端口探测（授权环境内）；
2. **云元数据**（`169.254.169.254`）：可能读到实例临时凭证——SSRF 高危评级的主因；
3. 访问内部服务（管理接口、未鉴权的 Redis/ES 等）；
4. 条件性 RCE（与特定服务交互）。

## 攻击场景

### 场景一：本机与内网探测
**目标**：确认请求发自服务端。**思路**：URL 指向 `http://127.0.0.1:port` 与内网网段，按响应差异（耗时/长度/报错）区分存活。
**payload**：`http://127.0.0.1:8080/`、`http://10.0.0.12/`
**结果**：不同端口响应差异暴露内部服务面——**仅限授权环境，控制请求量**。

### 场景二：云元数据读取
**目标**：评估云上部署的真实危害上限。**思路**：URL 指向元数据服务；新版云厂商要求带特殊头（如 IMDSv2 的 token 头），不带头的旧版直接可读。
**payload**：`http://169.254.169.254/latest/meta-data/iam/security-credentials/`
**结果**：读到临时凭证 = 从 SSRF 跃升为云账号资源可操作，评级直接拉满。

### 场景三：协议与内部服务利用
**目标**：非 HTTP 后端。**思路**：某些客户端支持 `gopher://`/`dict://`/`file://` 协议，可构造非 HTTP 交互（概念级）；Redis 未鉴权时经 SSRF 写键、条件性写文件。
**结果**：危害取决于「服务端出网客户端支持的协议集」——这就是修复要白名单协议的原因。

### 场景四：盲 SSRF 的带外确认
**目标**：响应不回显请求结果时。**思路**：URL 指向自控域名，用 DNS/HTTP 回连日志确认「服务端确实发了请求」。
**payload**：`http://<你的自控域名>/probe`
**结果**：回连记录就是 SSRF 的存在证据——大多数现代 SSRF 都是盲的，这条是主力手法。

## 怎么发现它
- **手工测试**：枚举一切「URL 输入点」（预览、导入、webhook、图片地址），先打自控域名确认出网，再逐级评估：本机 → 内网 → 元数据。每步都在授权范围内、控制节奏。
- **工具**：Burp Collaborator / 自建回连服务收信号；dnslog 类平台做快速确认。
- **真假判断**：回连到达 = 实锤；「请求超时」可能是目标端口关闭而非拦截；区分「应用层白名单拒绝（报错）」与「网络层不可达（超时）」——两者的绕过策略完全不同。

## 常见绕过与进阶
- **IP 表示法**：`127.0.0.1` → `2130706433`（十进制）/ `0177.0.0.1`（八进制）/ `::1`（IPv6）/ `0x7f000001`（十六进制）——校验若按字符串匹配黑名单全失效。
- **DNS rebinding**：域名第一次解析返回合法 IP 过校验，TTL 过后第二次解析返回内网 IP——「校验在解析前」的方案被击穿。
- **重定向**：合法外域 URL 返回 302 跳内网——「只校验首跳」的方案被击穿。
- **URL 解析差异**：`http://target.com@10.0.0.1/`（host 实为内网）、`\` 与 `/` 的解析分歧——与[开放重定向](../20-frontend/open-redirect.md)同一族解析器问题。
- 思路主线：**校验发生在「URL 字符串层」，而执行发生在「解析后的连接层」——两层之间的一切差异都是绕过面**。

## 怎么修
1. **出网白名单（治本）**：协议（仅 https）、域名（精确白名单）、端口、IP 段（禁环回/私网/链路本地）逐项限制；白名单在**解析出 IP 之后**按 IP 复核（防 rebinding）。
2. **禁跟随重定向**，或每一跳都重新走完整校验。
3. **网络层隔离（纵深，云环境必做）**：应用容器出网走代理/ACL，元数据服务加防火墙规则（IMDSv2 强制），内网服务互访最小化——「即使 SSRF 也够不到」比「拦住所有 payload」可靠。
4. **响应不回显**：预览类功能只返回处理结果，不透传原始响应体。
5. **禁用非必要协议**：客户端库关闭 `gopher`/`file` 等协议支持。

## 常见误区
- **「SSRF 只能探测内网，危害低」**：云元数据凭证一经读出，危害上限是整个云资源面；评级必须先确认部署环境是否在云上。
- **「过滤了 127.0.0.1 就安全」**：IP 有无数种写法，且真正目标是 `169.254.169.254` 与内网段——黑名单思路在 IP 上尤其失效。
- **「HTTPS 了就安全」**：SSRF 与传输加密无关；恰恰要注意「https URL 也能打内网 http 服务」。
- **「没有回显就没有 SSRF」**：盲 SSRF 靠带外确认即可成立，且回连本身就是证据。
