# Web 缓存攻击（缓存欺骗与缓存投毒）

## 一句话
> 缓存的两个安全假设——「这个 URL 的响应对所有人一样」与「进缓存键的内容决定响应内容」——只要有一个不成立，就会出现「骗缓存存下你的私人页面」（缓存欺骗）或「把恶意内容注入所有人看到的页面」（缓存投毒）。

## 它是怎么发生的
**根因**：CDN/代理缓存为了性能，按「缓存键」（通常是 path+query 的子集）存储响应并复用给后续请求。安全前提有两条，各自的破坏对应一种攻击：

| 攻击 | 被破坏的假设 | 一句话过程 |
|------|-------------|-----------|
| **缓存欺骗**（Deception） | 「私人响应不会被缓存」 | 诱导受害者访问 `/profile/x.css`——扩展名让缓存以为「这是静态资源」而缓存了她的私人页面，攻击者随后请求同一 URL 读缓存 |
| **缓存投毒**（Poisoning） | 「键决定内容」 | 某个**不进缓存键却影响响应**的输入（某 header、未键入的 query 参数）被注入恶意值，带毒响应被缓存并返回给所有后续用户 |

**共同的触发结构**：缓存层与应用层对「什么影响响应」的理解不一致——缓存以为无关的输入，应用却在用。

## 攻击场景

### 场景一：缓存欺骗（读他人数据）
**目标**：返回个人数据的页面。**思路**：给路径加一个「静态资源尾巴」+ 独特标识：
**payload**：`https://target.com/account/settings/nonexistent.css`（受害者从攻击页点击此链接）
**结果**：缓存按 `.css` 判定可缓存 → 存下 settings 页 → 攻击者请求同一 URL → 命中受害者页面的缓存。成立条件：缓存规则按扩展名/路径模式放行 + 页面无 `Cache-Control: private/no-store`。

### 场景二：未键入参数投毒（基础形态）
**目标**：响应中回显某输入的接口（如导航高亮、UTM 参数）。**思路**：找「改了它响应就变、但它不在缓存键里」的参数：
**payload**：`https://target.com/?utm=xxx<script-src-evil></script>`（概念示意）
**结果**：第一个请求把带毒响应写入缓存，之后所有访问同 URL 的用户都收到——一次投毒，全体受害。落地常接[XSS](../20-frontend/xss.md)。

### 场景三：header 投毒
**目标**：应用把 `X-Forwarded-Host`/`X-Forwarded-For` 之类 header 用于生成内容（绝对链接、JS 地址）。**思路**：改 header 发请求，观察响应是否变化且被缓存。
**结果**：资源地址被指向攻击者域——与[SSRF](../40-files-requests/ssrf.md)、[开放重定向](../20-frontend/open-redirect.md)常在同一批「服务端信任可伪造 header」的点里出现。

### 场景四：胖 GET（Fat GET）
**目标**：应用忽略 query 但缓存按完整 URL 键入。**思路**：`GET /?cache_buster=x` 与 `GET /` 在应用看来相同、在缓存看来不同——用带体参数的 GET 让「同键不同响应」。
**结果**：探测缓存行为差异的基本手法之一。

## 怎么发现它
- **手工测试（缓存行为测绘法）**：
  1. 先证「有没有缓存」：响应头找 `Age`、`X-Cache: HIT/MISS`、`Cache-Control`；连发两次同请求看第二次是否 HIT；
  2. 摸清「键是什么」：逐个改 path/query/标准 header，看哪些变化导致 MISS（= 在键里）；
  3. 找「影响响应却不在键里」的输入：改它 → 响应变 + 仍 HIT = 投毒候选点；
  4. 欺骗面：测「私人页面 + 静态尾巴」是否被缓存（用无痕会话验证缓存里确实有私人数据）。
- **真假判断**：HIT 不代表可利用——要看「缓存里的内容是否含敏感数据」（欺骗）或「键外输入是否真影响响应」（投毒）；自建/本地缓存（浏览器缓存）不算共享缓存攻击面。

## 常见绕过与进阶
- **键含全 URL**：加 cache buster 让自己的探测不污染他人视图（测试礼仪），同理攻击者用它精准投毒特定入口。
- **规范化差异**：缓存与应用对 `%2e`、分号参数（`path;k=v`）的规范化不一致——一处「键内」另一处「键外」，投毒面由此打开。
- **响应头反射**：`X-Original-URL` 类自定义头被应用使用时同样可作为键外输入。
- 思路主线：**测绘「键 vs 影响」两个集合，差集就是攻击面**。

## 怎么修
1. **缓存键覆盖一切影响响应的输入**（治本）：header 用于生成内容就必须进键，或干脆不使用不可信 header。
2. **敏感页禁缓存**：个人中心、账户设置类响应带 `Cache-Control: private, no-store`——缓存欺骗的直接解。
3. **按 URL 模式缓存白名单**：只缓存确定的静态路径，而非「按扩展名猜」——欺骗攻击依赖的正是「猜测规则」。
4. **输入不进响应头/绝对链接**：`X-Forwarded-*` 用于链接生成时必须白名单域。
5. **CDN 配置审计**：缓存规则与应用路由联合评审——「缓存层的规则」与应用「哪些 URL 有副作用/有私人数据」对齐。

## 常见误区
- **「有 CDN 就会有缓存攻击」**：攻击面取决于缓存规则与键设计；「只缓存明确静态路径 + 敏感页 no-store」的实现基本免疫。测出「可缓存」不等于可利用。
- **「缓存欺骗和缓存投毒是一回事」**：欺骗读他人的缓存（受害者自投罗网），投毒写恶意的缓存（毒害所有后来者）——方向相反，修复点也不同。
- **「投毒只影响我自己」**：共享缓存的定义就是「多用户复用」——一次投毒影响所有命中该键的请求，危害按「被毒 URL 的流量」评估。
- **「浏览器缓存也算」**：本地缓存只影响自己，构不成跨用户攻击；本条目讨论的是共享缓存（CDN/反向代理）。
