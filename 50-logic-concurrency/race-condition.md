# 竞态条件（Race Condition）

## 一句话
> 「检查」和「执行」之间有时间窗，多个请求挤进同一窗口时全部通过了同一次检查——优惠券领一次变领十次。它是一切「一次限额」类规则在并发面前的通病。

## 它是怎么发生的
**根因**：TOCTOU（Time-of-Check to Time-of-Use）——代码先「检查条件」（余额够吗？券领过吗？）再「执行动作」（扣款、发券），两步之间有毫秒级窗口。单线程世界没问题；并发世界里**多个请求在窗口内同时通过了同一个尚未变化的检查**，然后逐个执行。

```
请求A: 检查余额(100) ✓ ──────→ 扣款 100   → 余额 0
请求B: 检查余额(100) ✓ ──────→ 扣款 100   → 余额 -100（本应失败）
        ↑ A、B 的检查都发生在任何扣款之前
```

**Web 语境的触发三要素**：
1. 「检查 + 执行」非原子（读-改-写分步、跨数据库查询）；
2. 规则依赖「一次性」假设（限领一次、余额扣减、库存、投票）；
3. 攻击者能让多个请求几乎同时到达（并发工具）。

**与[业务逻辑](business-logic.md)的关系**：竞态是逻辑漏洞的**并发特例**——串行重放被幂等挡住的，并发可能绕过；两者常一起测。

## 攻击场景

### 场景一：限额类重复领取
**目标**：优惠券/签到/邀请奖励（「每人限一次」）。**思路**：同一请求并发 N 发，所有请求都在「领过吗」检查更新之前通过。
**payload**：并发 20 发同一「领券」请求（授权环境的测试账号）。
**结果**：N 次成功 = 无原子性保证。

### 场景二：余额/提现双花
**目标**：提现、转账。**思路**：余额 100，并发发起两笔 100 提现。
**结果**：两笔都成功 = 检查与扣款非原子——资金类竞态是危害上限最高的一档。

### 场景三：库存超卖
**目标**：抢购。**思路**：库存 1，并发下单 N 个。
**结果**：全部下单成功 = 超卖，同场景二属于「读-改-写」非原子。

### 场景四：单包攻击（Last-Byte Sync，概念）
**目标**：让请求「同时到达」更极致。**思路**：HTTP/2 单连接上发多个请求、只留最后一个字节不发，随后一齐释放——所有请求在同一瞬间抵达后端，把窗口利用推到极限。
**结果**：这是现代竞态利用的标准技术形态；测试中理解原理即可，授权环境下用成熟工具控制并发量。

## 怎么发现它
- **手工测试（成对对照法）**：先单发确认功能正常 → 并发 N 发同一请求 → 查服务端最终状态（券领了几张、余额扣了几次）。以**数据库最终状态**为准，不以响应为准。
- **工具**：Burp 的 Race 功能 / Turbo Intruder 类并发工具；自写脚本（多线程/多连接同步）。
- **真假判断**：部分成功（10 发中 2 发成功）也可能是限流拦截——区分「被限流」与「被原子性挡住」要看响应内容与状态；重复三次实验，单次结果不稳定正是竞态的特征（它本质是概率性的）。

## 常见绕过与进阶
- **限流绕过**：并发窗口被限流器挡住时，分散到多会话/多 IP/低频重试——但真正的修复（原子性）与限流无关。
- **会话复用**：多连接共享同一会话 vs 多会话并行，两种到达形态都要试。
- **窗口探测**：检查逻辑越复杂（跨服务、跨表），窗口越大——微服务架构下竞态面反而更宽。
- 思路主线：**每个「一次限额」假设 + 每个「读-改-写」模式 = 一个竞态候选点**。

## 怎么修
1. **数据库唯一约束（最可靠）**：「每人一张券」= `UNIQUE(user_id, coupon_id)`——并发再猛也插不进第二行，把「检查」下沉为「约束」。
2. **原子更新**：`UPDATE accounts SET balance = balance - 100 WHERE balance >= 100`（条件更新），或乐观锁（版本号）；绝不在应用层「先查后改」。
3. **互斥锁**：热点账户/库存用行锁或分布式锁串行化关键段——代价是吞吐，用在刀刃上。
4. **幂等设计**：与[业务逻辑](business-logic.md)修复共用幂等键；幂等挡重放，原子性挡并发，两者互补。
5. **限流只是缓解**：它压缩并发利用的效率，不消灭窗口——不要把限流当修复写进报告结论。

## 常见误区
- **「Web 是多线程天然并发的，所以到处都是竞态」**：只有「检查与执行分离且结果依赖检查」的写操作才有可利用竞态；纯读操作不构成危害。
- **「加个限流就好了」**：限流挡效率不挡正确性，并发窗口仍在——资金类操作必须原子性修复。
- **「测试一次就下结论」**：竞态是概率性的，单次并发不成功可能是时序运气，需多轮实验。
- **「只有高并发业务才需要关心」**：领券、绑定、激活类「低频但限额」的操作同样可被单包攻击在一瞬间击穿。
