# 安全配置错误（Security Misconfiguration）

## 一句话
> 代码没写错，但系统「出厂状态」直接上了线——默认口令、调试端点、多余功能、过时组件。它是 A05 类的汇总条目：凡是「改配置就能修」的问题都住在这里。

## 它是怎么发生的
**根因**：安全基线（secure baseline）缺位——部署时「能跑就行」，默认配置原样进生产。四个高频来源：

| 来源 | 典型问题 |
|------|----------|
| 默认凭据与默认页面 | admin/admin、示例应用（如 Tomcat manager）未删 |
| 暴露的管理与调试面 | `/admin`、`/actuator`、phpMyAdmin 直接公网可达 |
| 多余的功能 | 不用的方法（OPTIONS 全开、TRACE）、示例接口、目录列举 |
| 过时组件与错误配置 | 带已知 CVE 的依赖、弱 TLS、云存储桶公开读写 |

**为什么它常年霸榜**：配置漂移是持续发生的——每次加服务、升组件、改防火墙都可能引入新缺口，而「能跑」永远优先于「安全」。它也是[信息泄露](info-disclosure.md)的母类：泄露面大多是配置问题。

## 攻击场景

### 场景一：默认凭据
**目标**：管理后台、监控面板、数据库管理页。**思路**：先识别产品（报错页、favicon、特征路径），再对照默认口令表。
**payload**：admin/admin、admin/password、厂商默认值
**结果**：登录成功 = 无需任何漏洞利用的直接接管——所有测试的第一轮都应过一遍常见管理入口。

### 场景二：调试端点暴露
**目标**：Spring Boot Actuator、Flask debug、phpinfo。**思路**：请求固定路径核对内容。
**payload**：`GET /actuator/env`、`GET /actuator/heapdump`
**结果**：`env` 给配置与密码、`heapdump` 给内存（含会话与密钥）——与[信息泄露](info-disclosure.md)联动直接升级。

### 场景三：过时组件
**目标**：带已知 CVE 的组件。**思路**：从报错、响应头、favicon hash 识别版本 → 对照 CVE 库匹配 → 在授权环境验证可达性。经典案例 Log4Shell（CVE-2021-44228）：一个日志库的 JNDI 查询缺陷，让「在任意会打印日志的字段里提交一行字符串」升级为全网 RCE——它演示了「组件漏洞 × 随处可达的输入面」的传导模型。
**结果**：版本确认 + 可利用点 = 高危；现代攻防里「组件治理」就是主战场。

### 场景四：云存储桶与权限过宽
**目标**：对象存储（S3/OSS 类）。**思路**：确认桶是否公开列举、是否可匿名写；云服务 IAM 策略是否 `*`。
**结果**：公开读 = 数据泄露；公开写 = 内容注入与钓鱼托管——云配置错误已是独立的大类。

### 场景五：弱 TLS 与宽松方法
**目标**：传输与 HTTP 方法配置。**思路**：核 TLS 版本/套件、测试 TRACE/OPTIONS 是否全开、CORS 与安全头（接[CORS](../20-frontend/cors.md)、[点击劫持](../20-frontend/clickjacking.md)）。
**结果**：单项低危，但作为基线缺口成批出现时反映整体安全成熟度。

## 怎么发现它
- **手工测试（基线核对法）**：固定清单逐项过——默认口令表、常见管理/调试路径、HTTP 方法、TLS 配置、安全响应头、目录列举、云桶权限。配置错误的特点是「查得出来」而非「猜得出来」——清单就是生产力。
- **工具**：nuclei 类模板扫描器对「已知配置缺口」覆盖极好（这正是本类漏洞适合模板化的原因）；nmap/sslscan 核服务与 TLS。
- **真假判断**：管理路径 200 不等于可登录（要看认证）；`OPTIONS *` 开着只是信息面（除非 ALLOW 含危险方法）；组件版本要「确认可达的触发点」再定级，不能只报版本号。

## 常见绕过与进阶
- **管理端口改非标准位**：端口扫描 + 特征识别（favicon hash、报错页）仍可定位——改端口不是加固。
- **Basic Auth 保护的管理面**：弱口令爆破（授权环境、限速）与默认凭据仍是入口。
- **组件漏洞的变体触发**：主路径被滤时找「同样会到达 sink」的替代输入（如 Log4Shell 不止 payload 字段——任何进日志的字段都行）。
- 思路主线：**配置错误的对抗本质是「基线 vs 漂移」——测试用清单，防御也要用清单（否则永远在追）**。

## 怎么修
1. **安全基线文档化 + 自动核对**：对照 CIS Benchmark 建立各组件基线；基线是「清单」，IaC（配置即代码）让它可审计、可回归。
2. **默认全部改掉**：默认凭据、默认页面、示例应用上线前清零；安装向导强制改密。
3. **最小暴露面**：管理与调试接口绑内网/加鉴权；不用的方法与服务直接关闭（不是「不管它」）。
4. **组件治理**：依赖清单（SBOM）+ CVE 订阅 + 升级流程；已知高危 CVE 的组件限期修复。
5. **云配置治理**：存储桶默认私有、IAM 最小权限、开启配置审计（云厂商的 posture 管理工具）。

## 常见误区
- **「配置错误 = 低危杂项」**：默认凭据、公开存储桶、暴露的 actuator 都可单项直达接管；它是 A05 类，不是「边角料类」。
- **「改了管理端口、藏了路径就安全」**： obscurity 对端口扫描与特征识别无效；要靠鉴权与网络隔离。
- **「上了新版本就不用管组件」**：CVE 是持续产出的；没有 SBOM 与订阅流程，「当前安全」无法维持。
- **「这是运维的事，与开发无关」**：依赖选择（开发）与配置基线（运维）共同决定——配置错误是全生命周期的责任。
